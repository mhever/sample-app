# Architecture Overview - sample-app

This document explains the complete architecture, GitOps pipeline, and Kubernetes concepts used in this project.

## The Application

### Components
- **Go HTTP service** ([main.go](../main.go)) with the following endpoints:
  - `/` - Service info (name, version, hostname, time)
  - `/healthz` - Liveness probe (always 200 if process alive)
  - `/readyz` - Readiness probe (returns 200 only when DB reachable)
  - `/metrics` - Prometheus metrics endpoint
  - `/env` - Config inspection
  - `/work?ms=200` - Simulated work/latency
  - `/kill` - Chaos testing (simulates crash)

- **PostgreSQL database** - Used for readiness checks and application data
- **Multi-stage Docker build** - Runs tests during build, creates minimal Alpine-based image

## GitOps Pipeline - End to End

```
1. Developer commits code to main branch
   ↓
2. GitHub Actions: build-and-push.yml
   • Triggers on: push to main (for *.go, go.mod, go.sum, Dockerfile changes)
   • Builds Docker image using multi-stage Dockerfile
   • Runs tests during build (go test ./...)
   • Tags image with git SHA (sha-XXXXXXX format, 7 characters)
   • Pushes to ghcr.io/mhever/sample-app
   • Uses GitHub Actions cache for faster builds
   ↓
3. GitHub Actions: bump-kustomize-tag.yml
   • Triggered by: successful completion of build-and-push workflow
   • Extracts 7-character SHA from completed workflow
   • Updates k8s/overlays/home/kustomization.yaml
   • Sets newTag: sha-XXXXXXX
   • Commits change with "[skip ci]" to prevent infinite loop
   • Pushes to repository
   ↓
4. Flux CD (running on K3s cluster)
   • Polls Git repository every 1 minute (interval: 1m)
   • Detects change in kustomization.yaml
   • Pulls new manifests from repository
   • Applies changes to cluster (reconciliation)
   • Waits for successful deployment (wait: true, timeout: 2m)
   ↓
5. Kubernetes Deployment
   • Pulls new image from GitHub Container Registry
   • Performs rolling update of 3 replicas
   • Waits for readiness probes to pass
   • Prometheus automatically discovers and scrapes new pods
   • Old pods terminated after new ones are ready
```

## Kubernetes Architecture

### Directory Structure

```
k8s/
├── base/                                    # Reusable base configurations
│   ├── app/                                 # Application manifests
│   │   ├── deployment.yaml                  # Pod template, probes, env injection
│   │   ├── service.yaml                     # ClusterIP service on port 80→8080
│   │   ├── configmap.yaml                   # Non-sensitive configuration
│   │   └── kustomization.yaml               # Kustomize base definition
│   └── postgres/                            # Database manifests
│       ├── deployment.yaml                  # PostgreSQL deployment
│       ├── service.yaml                     # Database service
│       ├── pvc.yaml                         # Persistent storage claim
│       └── kustomization.yaml               # Kustomize base definition
└── overlays/
    └── home/                                # Environment-specific overrides
        ├── namespace.yaml                   # Creates 'home' namespace
        ├── kustomization.yaml               # 🎯 Image tag updated here by CI/CD
        └── app-prometheus-annotations-patch.yaml  # Adds Prometheus scraping hints
```

### Kustomize Configuration

**Base Configuration** (`k8s/base/app/`)
- Defines core resources: Deployment, Service, ConfigMap
- Uses placeholder image: `sample-app:placeholder`
- Default replica count: 1
- Health probes configured
- Environment variables injected from ConfigMap and Secret

**Overlay Configuration** (`k8s/overlays/home/`)
- **Image transformation**: Replaces placeholder with `ghcr.io/mhever/sample-app:sha-XXXXXXX`
- **Replicas override**: Changes from 1 to 3 replicas
- **Namespace**: Deploys to `home` namespace
- **Patches**: Adds Prometheus annotations for metrics scraping

### Current Deployment State

- **Image**: `ghcr.io/mhever/sample-app:sha-8644a17`
- **Replicas**: 3 instances running
- **Namespace**: `home`
- **Service Type**: ClusterIP (internal cluster access)
- **Port Mapping**: Service port 80 → Container port 8080

### Health Checks

**Liveness Probe**
- Endpoint: `GET /healthz`
- Purpose: Detects if process is alive
- Action if fails: Kubernetes restarts the pod
- Initial delay: 5 seconds
- Check interval: 10 seconds

**Readiness Probe**
- Endpoint: `GET /readyz`
- Purpose: Checks if database is reachable
- Action if fails: Removes pod from service endpoints (no traffic sent)
- Initial delay: 5 seconds
- Check interval: 10 seconds

## Flux CD Configuration

**Flux System Location**: `clusters/home/flux-system/`
- Contains Flux GitOps Toolkit components
- Auto-generated by Flux bootstrap

**Application Kustomization**: `clusters/home/apps.yaml`
```yaml
kind: Kustomization
metadata:
  name: home-stack
  namespace: flux-system
spec:
  interval: 1m              # Check for changes every minute
  path: ./k8s/overlays/home # Path to manifests in repo
  prune: true               # Remove resources deleted from Git
  wait: true                # Wait for resources to be ready
  timeout: 2m               # Timeout for readiness
  sourceRef:
    kind: GitRepository
    name: flux-system       # Points to this repository
```

**How Flux Works**
1. Flux watches the Git repository for changes
2. When changes detected, pulls latest manifests
3. Compares desired state (Git) vs actual state (cluster)
4. Applies differences to reconcile cluster to match Git
5. Waits for all resources to become ready
6. Reports status back to Flux controllers

## Monitoring with Prometheus

### Metrics Collection

**Prometheus Annotations** (applied via patch)
```yaml
prometheus.io/scrape: "true"    # Enable scraping
prometheus.io/path: "/metrics"   # Metrics endpoint path
prometheus.io/port: "8080"       # Port to scrape
```

**How It Works**
- Prometheus running on K3s cluster discovers pods with these annotations
- Automatically scrapes `/metrics` endpoint every 15-30 seconds (configurable)
- Application exposes Go runtime metrics + custom metrics
- Metrics stored in Prometheus time-series database
- Can be visualized with Grafana or queried with PromQL

## Kubernetes Concepts in Use

### Core Concepts

| Concept | Usage in This Project | Learning Resources |
|---------|----------------------|-------------------|
| **GitOps** | Flux continuously reconciles Git repository state to cluster | Entire pipeline is declarative and version-controlled |
| **Kustomize** | Base/overlay pattern for environment-specific configs | Separates common resources from environment overrides |
| **Deployments** | Manages the desired state of 3 application replicas | Ensures pods are running and handles updates |
| **ReplicaSets** | Created automatically by Deployment | Maintains the specified number of pod replicas |
| **Services** | ClusterIP service provides stable internal endpoint | Load balances traffic across healthy pods |
| **ConfigMaps** | Stores non-sensitive configuration (DB host, etc.) | Injected as environment variables |
| **Secrets** | Stores sensitive data (DB password) | Injected as environment variables |
| **Namespaces** | Logical isolation using 'home' namespace | Separates resources from other apps |
| **Probes** | Liveness and Readiness probes for health monitoring | Enables automatic healing and traffic management |
| **Rolling Updates** | Gradual replacement when new image deployed | Zero-downtime deployments |
| **Observability** | Prometheus metrics, structured logging | Monitor application health and performance |
| **Persistent Volumes** | PostgreSQL data persists across pod restarts | PVC claims storage for database |

### Advanced Patterns

**Declarative Configuration**
- Everything defined as YAML manifests in Git
- No manual `kubectl apply` commands needed
- Full audit trail of all changes via Git history

**Immutable Infrastructure**
- Each deployment uses a specific SHA-tagged image
- No in-place updates; always deploy new images
- Easy rollback by reverting Git commit

**Self-Healing**
- Kubernetes automatically restarts failed pods (liveness probe)
- Removes unhealthy pods from service (readiness probe)
- Maintains desired replica count even if nodes fail

**GitOps Benefits**
- **Single source of truth**: Git repository defines entire system state
- **Auditability**: Every change tracked with Git commit history
- **Rollback**: Easy to revert to previous working state
- **Consistency**: Same process for all environments
- **Security**: No direct cluster access needed for deployments

## CI/CD Pipeline Details

### Workflow 1: Build and Push (`build-and-push.yml`)

**Triggers**
- Push to main branch (when Go files, go.mod, go.sum, or Dockerfile change)
- Pull requests to main
- Manual workflow dispatch

**Steps**
1. Checkout code
2. Set up Docker Buildx (for multi-platform builds)
3. Login to GitHub Container Registry (GHCR)
4. Generate Docker metadata (tags and labels)
5. Build Docker image with caching
6. Run tests during build (in Dockerfile)
7. Push image to `ghcr.io/mhever/sample-app`

**Image Tags Created**
- `sha-XXXXXXX` (7-character SHA)
- `main` (branch name)

### Workflow 2: Bump Kustomize Tag (`bump-kustomize-tag.yml`)

**Triggers**
- Successful completion of `build-and-push` workflow

**Steps**
1. Checkout repository
2. Extract 7-character SHA from triggering workflow
3. Update `k8s/overlays/home/kustomization.yaml` with new tag
4. Commit with "[skip ci]" message to prevent loop
5. Push commit to trigger Flux reconciliation

**Important**: The `[skip ci]` marker prevents this commit from triggering the build workflow again, avoiding an infinite loop.

## Troubleshooting

### Pod Not Starting
1. Check pod status: `kubectl describe pod -n home <pod-name>`
2. Check logs: `kubectl logs -n home <pod-name>`
3. Common issues:
   - Image pull errors (check GHCR permissions)
   - ConfigMap/Secret missing
   - Resource limits exceeded

### Readiness Probe Failing
1. Pod is running but not receiving traffic
2. Usually means database is unreachable
3. Check: `kubectl logs -n home <pod-name>` for DB connection errors
4. Verify PostgreSQL pod is running: `kubectl get pods -n home`

### Flux Not Reconciling
1. Check Flux logs: `flux logs`
2. Check source status: `flux get sources git`
3. Force reconciliation: `flux reconcile kustomization home-stack`
4. Common issues:
   - Git authentication problems
   - Syntax errors in YAML
   - Resource conflicts

### Image Not Updating
1. Check GitHub Actions workflows succeeded
2. Verify kustomization.yaml was updated with new tag
3. Check Flux reconciliation interval (1 minute)
4. Force reconcile if needed: `flux reconcile kustomization home-stack`
